### How scoring logic works:

- We first have written a function that imports some amount of generated decks as a numpy array of numpy arrays. This is import_decks in src/scoring.py
    (ex: [[0,1,1,0,1, ...],[1,0,0,1,0,...]])
- This is written explicitly to use our data generated by data generation method 1. This is because we reasoned it is easier to read. The data should be identical between the two, and in the future we could implement an option to read from either, if this was being set up as a pipeline of some kind.
- We then wrote a function that scores one deck, which is inputted as a numpy array. This is score_a_deck in src/scoring.py. For this deck we
    1. Iterate through the entire deck starting at index 0, and append each 'card' (0 or 1) to a list called running_sequence.
    2. As soon as len(running_sequence) > 2 (So, the length is 3 or greater, meaning it is possible to check for a sequence), we start to check its final 3 items. 
    3. If those three final items are identical to a player's input combination of cards, we add +1 to the counter signifying the number of tricks they have won, and we add the length of the running sequence to the counter signifying the number of cards they have won. We then reset the running_sequence to an empty list, and continue the process of appending cards and checking to see if the running sequence is long enough.
    4. When the entire deck is finished going through this sequence, we finalize a score for the game. Whichever player has the higher number of cards obtains +1 for their win, whichever player has the higher number of tricks obtains +1 for their win, and if both players had the same number of cards there would be a +1 in terms of draws scored on cards (and the same if both players had the same number of tricks). Results are returned as a dictionary.
- Then we created a function (batch_score_all_combos in src/scoring.py) that generates all 56 valid combinations of decks, and then takes in an array of decks as its input, and for each of the 56 possible valid games it runs the scoring function on each deck of cards in the array, and sums the scores to get the final statistics for each player's wins, losses, and draws by both cards and tricks. The results are returned as a pandas dataframe.

### Other approaches we tried:

We thought initially that our function to score one deck should be completed using a sliding window technique, where instead of appending each card to a python list and indexing its last 3 items, we would have two pointers that index the 3 values for comparison from the inputted deck of cards. This code is visible in our 'src/scoring.py' file, but is not actually used in our final deck scoring process. We thought that using pointers would shorten the program's runtime because we would not have to continuously generate, append, and index a python list, but instead only index the input that already exists in the program. Upon testing, however, we noticed that both methods performed almost the same, however the pointer function took milliseconds longer than the running_sequence python list function, which would quickly add up on the scale of 2 million decks. We suspect that this is because omitting the use of a list means that more actual indexing operations are performed in the code, and those operators add up to more runtime usage than just using the python list method.
